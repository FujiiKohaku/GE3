# Playerの戦闘処理をBattleへ移す実行計画

> 方針変更：移動処理と移動用データはPlayer直下の `Movement/PlayerMovement`、入力機器の読み取りと操作方式の選択は `Input/PlayerInput` へ分離する。Playerは操作値を照準・Movementへ渡し、照準計算と公開APIを保持する。武器側の射撃入力は今回の入力分離に含めない。以下は分離前の当初計画であり、移動先とデータ所有に関する記述はこの方針へ置き換える。

## 目的と前提

`Player.cpp` に残っている通常戦闘中の入力・照準・操縦・被弾処理を、既存の `States/Battle/PlayerBattleState` へ移す。
`Player` は外部向けAPI、状態遷移、共有データ、モデル描画を担当する。
操作感・発射条件・更新順序・死亡演出は維持する。

本書は実装前の計画。コード変更・ビルド・テスト実行は行っていない。
実装は変更許可を受けてから開始する。

## 実行コスト

- 現在の計算を配置し直すため、フレーム単位の計算量と弾数に対する計算量は基本的に変わらない。
- 公開APIからBattleへの委譲により、関数呼び出しが増える箇所はある。インライン化されるかはビルド設定によるため、増加時間を数値で保証しない。
- Stateは既存の値メンバーを使用し、新しい動的確保や仮想関数によるState管理は導入しない。
- 初回は既存データの配置を維持するため、大きなメモリ増加は想定しない。正確なサイズは必要に応じて実装後に確認する。
- `Player.h` の変更で関連ファイルの再コンパイルが発生する。テストはゲーム側のオブジェクトを再利用する構成があるため、ゲーム本体を先にビルドする。所要時間は未計測。

## 現状の注意点

- `PlayerBattleState::Update` はすでに照準・移動・武器の更新順序を管理しているが、主要な処理本体は `Player` のprivate関数にある。
- `GamePlayScene` はレール進行の前に `UpdateBoostState`、カメラ更新後に `ConstrainGamepadAimToPlayer` を呼ぶ。照準補正は別のシーン処理からも呼ばれる。
- ブースト更新はシーン側とBattle側の両方から呼ばれている。今回の移動に合わせて呼び出し回数を変更しない。
- `PlayerDeadState::Enter` は `StopMovement` とロック解除を使用する。
- 死亡後も `PlayerDeadState::Update` が発射済みの弾を更新・削除する。
- `PlayerWeaponController` はPlayerの姿勢を参照し、照準レイ・照準位置・速度もPlayer経由で取得する。
- 現在の被弾・回復処理はBattle状態だけに限定されていない。既存テストには初期状態のPlayerに対して被弾させるケースがある。
- `PlayerTestAccess` は移動・照準・無敵時間などのprivate関数にアクセスしている。
- 既存の作業差分を保持し、今回の移動と無関係な修正は含めない。

## 移動先と責務

初回は処理本体の移動を優先する。Battle専用データの所有先変更は別工程とし、PlayerとBattleで同じデータを二重に保持しない。

| 対象 | 方針 |
| --- | --- |
| 入力方式の選択 | `GetControlInputType`、`GetControlInput`、`UpdateAimFromInput`、`UpdateAimSteering` と補助型をBattleへ移す |
| 照準 | `InitializeAim`、マウス・パッド照準更新、照準範囲制限、照準レイ・収束点・照準距離の計算をBattleへ移す |
| 操縦 | `UpdateMovement`、`UpdateBoost`、`UpdateSteering`、`UpdateRoll` と関連する解除処理をBattleへ移す |
| 飛行 | 全方向移動、機首方向、範囲内への復帰、高度・位置・バンク更新をBattleへ移す |
| レール移動の計算 | 初期化、位置・姿勢同期、レール位置適用、画面端補正、座標・速度計算をBattleへ移す。外部から設定するAPIはPlayerに残す |
| HP・無敵時間 | `ApplyHealthDamage`、`UpdateInvincibility`、回復計算をBattleへ移す。`ApplyDamage` と `Heal` はPlayerの公開窓口として残す |
| 外部からの照準・ブースト操作 | `UpdateBoostState`、`ConstrainGamepadAimToPlayer` はPlayerの公開APIを維持し、内部処理をBattleへ委譲する |
| 操作設定・飛行設定 | `SetControlMode`、`SetMouseSensitivity`、`EnableAllRangeMode` などは公開APIを維持し、内部状態の同期処理をBattleへ委譲する |
| 武器・弾・発熱・ロックオン | 既存の `Combat/Weapon` と `Combat/Bullet` に残す。Battleは戦闘中の更新を呼び出す |
| 状態遷移 | `ChangeState`、`Update` の状態分岐、死亡判定後のDeadへの遷移はPlayerに残す |
| 描画と共有データ | モデル、カメラ参照、Transform、HP、照準値、移動データ、武器所有、描画処理は初回ではPlayerに残す |
| 死亡演出 | `PlayerDeadState` に残す。戦闘操作を停止する処理だけ必要に応じてBattleへ委譲する |

既存の `friend class PlayerBattleState` を利用し、Battleの処理には必要な `Player&` または `const Player&` を渡す。
Playerを指す永続ポインターをBattleへ追加せず、既存の寿命関係を維持する。
補助型をBattleへ移しても `Player::ControlMode` の外部向け定義は維持する。

## 実行手順

1. **変更前の基準を確認する**
   - 作業差分を確認し、今回の対象を分離する。
   - 既存のPlayer関連テストとゲーム本体をビルドして、変更前からの失敗を記録する。
   - Battleから呼ぶ関数、シーン・Dead・武器・テストから呼ぶ関数を対応表にする。

2. **入力・照準を移す**
   - `PlayerBattleState.h/.cpp` に処理本体を移す。
   - 武器が使う `CreateAimRay`、`ResolveAimPoint` はPlayer側の薄い委譲関数で接続する。
   - 公開照準APIと初期化からBattleを呼び出す。照準初期化をBattle開始時だけに限定しない。
   - `PlayerTestAccess` の対象だけ更新し、入力・照準の既存テストを確認する。

3. **操縦・移動を移す**
   - ブースト、操舵、ロール、全方向飛行、レール位置計算と画面端補正を移す。
   - 位置・回転・レール設定APIから内部状態の同期を維持する。
   - Dead開始時の移動停止を接続し、ブースト・速度・ロールの解除を維持する。
   - シーン側のブースト更新とカメラ更新後の照準補正は、元の位置から呼び続ける。

4. **HP・無敵時間を移す**
   - 被弾の可否、HP下限、回復上限、無敵時間、効果音の条件を維持して移す。
   - `Player::ApplyDamage` は処理結果を受けて `ChangeState(State::Dead)` を行う。
   - Battleへ移したことを理由に、Entryでの被弾・回復を拒否する条件を追加しない。
   - `ShouldDraw` はPlayerに残し、被弾点滅とDead側の描画判定を維持する。

5. **依存関係と重複を整理する**
   - Battle内部から移動済み処理を直接呼び、Playerとの往復を不要に増やさない。
   - Playerに残す委譲関数は公開API、武器、他Stateなどから必要なものに限定する。
   - 不要になった宣言・includeだけを削除する。移した処理に必要なincludeはBattle側へ追加する。
   - ファイル追加・分割が必要になった場合だけ、ゲームとテストのプロジェクト登録を更新する。

6. **最終検証を行う**
   - ゲーム本体を先にビルドし、その後に関連テストをビルド・実行する。
   - 実機で入力・照準・飛行・被弾・死亡後の挙動を確認する。
   - 差分チェックで、今回と無関係な変更や処理の取り残しを確認する。

## 維持する更新順序

`PlayerBattleState::Update` の現在の順序を維持する。

1. 入力参照の確認、無敵時間更新、ブースト更新。
2. 通常操作中の照準更新、画面内制限、パッド照準補正、移動。
3. レール位置適用、移動後のパッド照準補正、照準距離更新。
4. Transform反映、武器入力更新、弾更新、無効弾の削除、モデル更新。
5. デバッグ用の照準描画。

未初期化、時間停止、入力参照なし、デバッグカメラ中の既存の早期終了・操作抑止条件も維持する。
EntryからBattleへ移ったフレームでBattle更新が行われる動作を維持する。

## 検証項目

- 既存の `PlayerMovementControllerTests`、`PlayerMovementPartsTests`、`PlayerHealthTests`、`PlayerWeaponHeatTests`、`GameplayCollisionTests` を対象にする。
- `PlayerControlTests.h`、武器リセット・武器別動作のテストは、それらを呼ぶ既存のテスト実行単位で確認する。
- テスト用アクセス経路は移動先へ合わせる。既存の期待値は今回の移動を理由に変更しない。
- 状態間の接続に既存テストの不足がある場合だけ、死亡時の停止や委譲後の照準参照などの振る舞いを確認するテストを補う。
- 手動確認：KeyboardAndMouseとController、パッド優先、照準端・カメラ追従、レール飛行、全方向飛行、ブースト、ロール、武器切替、過熱、ロックオン。
- 境界確認：時間停止、デバッグカメラ、被弾点滅、無敵終了、回復上限、致死ダメージ、死亡後の発射禁止、発射済み弾の継続更新。

## 完了条件

- 対象の戦闘処理本体がBattleへ移り、Player側は公開窓口・共有データ・状態遷移・描画を中心とした構成になる。
- シーン、衝突判定、HUD、武器が利用する公開APIの互換性を維持する。
- 通常戦闘と死亡後の弾更新が、それぞれ従来の回数と順序で行われる。
- 関連ビルド・テスト・手動確認の結果を記録し、未確認事項があれば明示する。
- 新規・変更コードには三項演算子とラムダ式を使用しない。移動対象内の既存の該当式は同等の名前付き関数やif文へ置き換える。
- 指定された命名規則に従い、対象外の既存名の一括変更をしない。

## 今回に含めない作業

Battle専用メンバーの所有先変更、State管理方式の変更、武器・弾の再設計、操作仕様の変更、既存のブースト呼び出し回数の見直しは別途扱う。
データの所有先変更を続けて行う場合は、公開Getter、武器の参照寿命、初期化、死亡処理の依存を確認した追加計画を作成する。
