# エフェクト編集API

`EffectManager`は既存の再生APIに加えて、以下を提供する。

| API | 動作 |
| --- | --- |
| `GetEffectConfig(name, config, error)` | 現在登録されているJSON全体をコピーする。未知の項目も保持する。 |
| `SaveEffectConfig(name, error)` | 登録時のJSONパスへ、現在の設定を種類付きで保存する。書き込み完了後に元のファイルを置き換える。 |
| `ApplyEffectConfigAndRestart(name, config, error)` | JSON全体を適用し、同名の再生中インスタンスをすべて再開始する。ファイルへは保存しない。 |
| `RestartEffect(handle, error)` | 指定インスタンスだけを現在の設定で再開始する。 |
| `ReloadEffectShaders(name, error)` | メモリ上の設定が指定するEmit・Update・Vertex・Pixelシェーダーを強制再コンパイルし、PSOを再作成して同名インスタンスを再開始する。 |

成功は`true`、失敗は`false`。失敗の理由は`error`に入り、成功すると消去される。未知の名前・無効なハンドルも失敗として返す。新しいAPIは登録済みエフェクトを対象とする。

## 呼び出しタイミング

再開始・設定適用・シェーダー再読み込みのAPIは、レンダースレッドで`DirectXCommon::PostDraw()`が返った直後、次フレームのコマンドを一切記録する前に呼ぶ。UIでは適用要求を保持し、フレーム終端で実行する。`GetCommandList()`で取得したポインターをフレームを越えて保持・使用しないこと。取得・保存はGPU命令を記録しないが、設定適用と並行して呼ばないこと。

エンジンはコマンドリストの取得や描画開始を検出すると、次の`PostDraw()`まで編集を拒否する。初期化直後のアップロードコマンドもあるため、初回は通常フレームを一度完了させる。適用後は通常どおり`EffectManager::Update()`、描画の順に進める。新しい粒子バッファのGPU初期化は次の`Update()`で実施する。

```cpp
// UIで変更したJSONを、PostDraw()直後に適用する例。
nlohmann::json config;
std::string error;
EffectManager* effects = EffectManager::GetInstance();
if (effects->GetEffectConfig("DamageHit", config, error)) {
    config["Particle"]["StartColor"] = { 0.1f, 0.3f, 1.0f, 1.0f };
    bool isApplied = effects->ApplyEffectConfigAndRestart("DamageHit", config, error);
    // isAppliedとerrorをエディターのUIに返す。
}
```

設定は部分更新ではなく完全なJSON。取得したデータを編集して渡す。取得・設定適用だけではJSONファイルを書き換えない。保存には`SaveEffectConfig()`を明示的に呼ぶ。保存先は登録時に指定したJSONパスで、パス未指定の場合はエラーを返す。同じ場所の`.tmp`へ書き込み、書き込み完了後に元のファイルを置き換える。既存の`.tmp`がある場合は上書きせずエラーを返す。

`Render.Type`は通常粒子が`"Mesh"`、トレイルが`"Trail"`。省略された既存JSONは`Mesh`として読み込み、取得・保存するJSONには必ず種類を明記する。古い平坦な形式の描画設定も維持する。登録後は種類を固定し、設定適用・同名の再登録による種類変更を拒否する。別種類のエフェクトは別名で新しく登録する。

## 切り替えと負荷

検証、シェーダー・PSO、テクスチャ、新しい再生用バッファの準備に成功してから切り替える。失敗時は実行中の定義と粒子バッファを維持する。準備中は旧・新バッファを両方持つため、一時的に追加GPUメモリとインスタンスあたり4個のディスクリプターが必要。足りなければ旧状態を維持して失敗する。

適用はGPU完了待ちを伴う。数値だけの編集では既存PSOを再利用し、通常フレームでのファイル監視・再コンパイルは行わない。再開始時はハンドル・位置・追従先と明示指定のループ／再生時間を維持し、粒子と経過時間をリセットする。定義由来のループ／再生時間は変更後の設定を使用する。再生中インスタンスがなければ定義だけを更新する。

`SetEffectDirection()`と`SetEffectSkeletonPose()`で渡した直近の方向・骨格情報も引き継ぐ。`SetEffectVelocity()`を一度でも成功させたインスタンスは、その直近の指定速度を維持する。明示的に指定したゼロ速度も維持する。速度を個別指定していないインスタンスは、変更後のJSONの`Particle.Velocity`を使う。これらは再開始・設定適用・シェーダー再読み込みに共通の動作で、個別指定を共有設定や保存JSONへ書き戻さない。停止後に新しく再生するインスタンスには引き継がず、プールから再利用するGPUデータも初期値へ戻す。

再開始するインスタンス自身が有効なポイントライトを持っている場合は、そのハンドルとシャドウ設定を維持して色・位置・強度・半径・減衰を更新する。別のインスタンスや別の場所のライトを転用しない。新規ライトが必要な場合は空き枠を確保し、足りなければ変更全体を中止する。準備中に確保したライトは失敗時に解放し、既存ライトの更新途中で失敗した場合は、それまでの更新も元に戻す。ライトを無効にする設定では対象インスタンス自身のライトだけを解放する。

シェーダー再読み込みはJSONをディスクから読み直す操作とは別。失敗したコンパイルの診断も`error`で返る。コンパイル済みDXILキャッシュは更新され得るが、元のHLSL・JSONは書き換えない。共通の初期化・フィールド用シェーダーやルートシグネチャの変更はこのAPIの対象外。

`Emitter.Count`と旧形式の`EmitCount`は0〜4096の整数。ファイル読み込み・設定適用時に検証し、発生用GPU命令の直前にも検証する。不正な実行時の値はログに記録して、その発生命令を出さない。0は発生なしとして扱う。

`MaxParticles`の検証範囲は1〜4096。付属するメッシュパーティクルの生成・更新シェーダーは`gEmitter.maxParticles`を参照し、共通フィールド処理には同じ容量をルート定数で渡す。独自に追加するシェーダーもこの容量に合わせる。トレイルの点数上限は従来どおり別管理。専用シェーダーに固定された色・挙動はJSONだけでは変更できない。シェーダーのバッファ定義・レジスター配置はエンジンの既存仕様に合わせる。デバイス喪失などGPU実行自体の障害からの復旧は別途必要。

## 検証

`project/Tests/EffectEditingTests.vcxproj`をRelease/x64でビルドし、`project`を作業ディレクトリにして`generated/outputs/Release/EffectEditingTests.exe`を実行する。非表示のモデルプレビューを描画環境として使用し、設定の反映、ハンドル維持、再開始、容量変更、シェーダー再読み込み、不正設定・欠落テクスチャ・コンパイル失敗時の状態維持、フレーム途中の適用拒否を検証する。

容量変更は1・17・255・256・257・1024・2048・4096個で実際のGPU粒子と空き番号を読み戻して検証する。発生数0・4096の境界、不正な発生数の設定拒否と実行時拒否、1024番を超える粒子への風の適用も確認する。
